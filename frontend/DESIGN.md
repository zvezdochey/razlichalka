# Различалка — дизайн-концепция и проект интерфейса

Дата: 6 ноября 2026. Предложение для реализации, а не описание готового приложения.

## 1. Идея продукта

«Понять последствия изменения стратегии до выката».

Пользователь — владелец СПР, риск-аналитик или разработчик стратегии. Интерфейс помогает ответить: сколько заявок затронуто, у скольких сменилось решение, какие проверки не прошли и где искать объяснение.

Главный принцип: каждое значимое число ведёт к данным, на которых оно посчитано. Путь: итог → разрез → список заявок → заявка → конкретный атрибут до и после.

Общий характер — спокойный аналитический инструмент. Высокая плотность полезной информации, ясная иерархия, заметные действия. Основную площадь занимают таблицы и сравнение значений.

## 2. Визуальный язык

Предлагаемые оттенки ниже — рабочая палитра, а не официальные бренд-токены заказчика.

| Назначение | Цвет |
|---|---|
| Фон рабочей области | `#F5F5F3` |
| Поверхность таблиц и панелей | `#FFFFFF` |
| Основной текст, шапка | `#181818` |
| Вторичный текст | `#626262` |
| Границы | `#DEDEDA` |
| Брендовый акцент, основные кнопки | `#C93620` |
| Оранжевый акцент | `#F08A32` |
| Успешная проверка | `#18704A` |
| Информационное выделение | `#2864A0` |

Белый рабочий холст, тонкие разделители, небольшое скругление 6–8 px. Красный используется точечно: основная кнопка, активный маркер, ошибка проверки. Оранжевый — для второстепенного акцента и внимания. Цвет кнопки не обозначает результат анализа.

Шрифт — системный sans-serif с хорошей кириллицей; код и пути — monospace. Основной текст 14–16 px, заголовок страницы 26–30 px, показатели 30–36 px. Табличные цифры одинаковой ширины, числа выровнены вправо. Отступы кратны 4 px, между крупными блоками 24 px.

Статусы всегда имеют текст и значок. Контраст основного текста и элементов проверяется при реализации; низкую уверенность показываем мягким фоном, сохраняя читаемый текст.

## 3. Каркас приложения

Сверху компактная тёмная шапка: знак Различалки, название текущего прогона и пользователь. Слева навигация шириной около 200 px: «Прогоны», «Конфигурации», «Процедуры и проверки». Это предложенная организация, а не требование заводить три независимых сервиса.

Внутри выбранного прогона — вкладки «Обзор», «Сводная», «Проверки», «Журнал». Контекст прогона остаётся видимым: датасет, BEFORE (MASTER), AFTER (BETA), статус, время запуска. Справа — «Повторить запуск» и, для готового отчёта, «Скачать HTML».

Первый экран нового пользователя — список прогонов с одной заметной кнопкой «Новый прогон». Строка списка: название, датасет, автор, статус, время, число заявок. Состояния и конфигурации разных пользователей должны быть разделены; ссылки открываются в пределах доступных пользователю данных. Конкретный способ входа согласуется с командой.

## 4. Настройка прогона

Одна страница с тремя последовательными секциями:

1. **Данные.** Выбор размещённого датасета, его имя, доступные срезы и известный объём. Загрузка архива может быть дополнительным способом, если её поддержит бэк. Прежний сценарий «загрузить два CSV» не принимаем за основной.
2. **Обработка.** Нормализация, сравнение, подготовка фактов. У каждой процедуры — переключатель «Рабочая область / Файл .py», выбранный обработчик, параметры и «Открыть код».
3. **Проверки.** Выбор набора, названия проверок, включение и параметры. Сразу предусмотрено подключение пользовательской проверки.

Внизу «Сохранить конфигурацию» и основная кнопка «Запустить». Сохранённую конфигурацию можно открыть и запустить повторно. Неопределённый датасет или неподключённая обязательная процедура отмечаются у соответствующего поля.

Рабочая область похожа на упрощённый notebook: название, Python-код, параметры, запуск и вывод. Рядом сворачиваемая справка по входам и результату. Для проверки виден контракт `CHECK` и `run(mart, params)`. Для других процедур показывается их согласованный контракт, без выдуманных сигнатур.

После изменения кода интерфейс различает «Есть несохранённые изменения», «Сохранено», «Исполняется», «Ошибка». Сохранение кода само по себе не запускает обработку. Версионирование и история редакций для задания не нужны.

## 5. Выполнение и журнал

После запуска открывается журнал: нормализация → сравнение → подготовка фактов → проверки. У этапа — состояние, время начала, длительность и диагностические сообщения. Порядок здесь описывает интерфейс; техническую зависимость этапов задаёт реализация.

Основной текст сообщает, что происходит: «Нормализуем ответы AFTER». Числовой прогресс показывается только при известном числе обработанных и общем объёме; иначе — индикатор активности и время выполнения.

Пользователь может перейти в другие разделы. Вкладки результатов до готовности объясняют: «Отчёт будет доступен после завершения обработки». Из строки журнала открывается текущий код связанного этапа; нельзя обещать исторический снимок исполненного кода, если его нет.

Ошибка этапа не выглядит как FAIL проверки: это отдельное состояние «Ошибка выполнения», с сообщением и ссылкой на код. Кнопка повторного запуска создаёт понятный новый запуск. Восстановление состояния после обновления страницы желательно и зависит от хранения состояния на бэке.

## 6. Обзор результата

Первый экран готового прогона даёт ответ за минуту.

Сверху четыре показателя: «Заявок в прогоне», «С различиями», «Сменили решение», «Проверки с FAIL». Подписи уточняют единицы: уникальные заявки, доля от объёма прогона, число строк результата проверок. Одна процедура может вернуть несколько строк, поэтому число строк FAIL не равно числу неуспешных процедур.

Под показателями — короткое резюме по рассчитанным данным: «Изменения чаще встречаются в …; основные сигналы проверок — …». Пока данных нет, используются пустые состояния; демонстрационные числа подписываются как пример. Приложение не выдаёт автоматическое разрешение на выкат без согласованных критериев.

Далее два блока: переходы решений BEFORE → AFTER и наиболее часто изменяемые атрибуты. Первый можно представить компактной матрицей, второй — горизонтальными полосами с числом уникальных затронутых заявок. Клик открывает соответствующую выборку. Дополнительно заметна категория «Различия есть, решение то же».

Сверху общие фильтры по доступным разрезам: продукт, тип партнёра, смена решения. Активные ограничения видны как подписи с кнопкой сброса. Если показатели пересчитаны по выборке, это явно написано рядом с ними.

## 7. Изменяемая сводная

Это центральный инструмент исследования. Вверху — «Раскладка», фильтры и «Сбросить». Редактор раскладки содержит области «Строки», «Колонки», «Фильтры», «Показатель». Поля можно выбирать кнопками; перетаскивание — дополнительное удобство.

Начальная раскладка: строки — иерархия пути атрибута, колонки — тип изменения и срез, показатель — агрегированные counts. Доступны сохранённые представления «По атрибутам», «По продуктам», «По решениям»; пользователь может менять состав и порядок измерений.

Четыре самостоятельных типа: «Значение изменилось», «Атрибут появился», «Атрибут исчез», «Без изменений». Они не подменяются прежними категориями `approve_to_reject` и `terms_changed`: те описывают другую ось анализа.

Сводная работает по агрегированным фактам. Нельзя суммировать counts по всем атрибутам и назвать итог числом уникальных заявок: одна заявка участвует в нескольких строках. Общий итог либо имеет корректную отдельную семантику, либо скрыт; рядом с показателем есть пояснение.

Нажатие на ячейку показывает её измерения, число заявок и список заявок. Выбранный контекст сохраняется при возврате. Если заявка встречается в нескольких продуктах, подпись объясняет пересечение групп.

## 8. От заявки до атрибута

Из ячейки открывается список заявок с ID, решениями до и после и числом изменённых атрибутов. Нажатие на заявку открывает широкую боковую панель; на небольшом экране — отдельную страницу с возвратом в исходную выборку.

Вверху карточки ID и решение BEFORE → AFTER. Ниже таблица «Атрибут / BEFORE / AFTER / Тип изменения», поиск по пути и переключатель «Только различия». Для массивов виден `ARRAY_KEY`: одинаковый PATH ещё не означает один и тот же элемент.

Отсутствие атрибута показывается как «Отсутствует», отдельно от `null`, пустой строки и нуля. Числовое изменение остаётся заметным, даже если оба значения попали в один бакет. Исходные значения и бакеты имеют разные подписи.

Пояснение причины опирается на проверку и наблюдаемые атрибуты. Например, изменение внешнего скора показывается отдельно от изменения модели или порога. Если причинность не доказана, формулировка — «Возможная причина» или «Связанные изменения», с указанием основания. Не каждое отличие автоматически объявляется следствием правки стратегии.

## 9. Единый отчёт проверок

Колонки: «Проверка», «Срез», «Аргумент», «Количество / база», «Метрика», «Результат», «Уверенность», «Заявки». Это отображение полей LABEL, SOURCE, ARGUMENT, CNT, TOTAL, METRIC, RESULT, CONFIDENCE, APP_IDS.

PASS — зелёная метка; FAIL с HIGH — выраженный красный сигнал; FAIL с LOW — мягкая подложка и текст «Низкая уверенность». LOW остаётся FAIL, а не превращается в PASS. Цвет не определяет порядок сам по себе: доступны фильтры и сортировка.

Количество заявок — ссылка в разбор. Если APP_IDS ограничен параметром проверки, показываем «Доступны N из M»; полный список нельзя обещать без отдельного получения выборки. Если ссылок нет, объясняем это вместо неработающей кнопки.

Действие «Добавить проверку» открывает рабочую область. После сохранения и применения её строки попадают в общую таблицу. Время последнего обновления и состояние выполнения видны; ошибка пользовательского кода показывается отдельно от результата PASS / FAIL.

## 10. HTML и мнение ИИ

Скачиваемый HTML содержит название и ID прогона, дату, датасет, итоговые показатели, единую таблицу всех проверок и абсолютную ссылку «Открыть сводную в приложении». Ссылка сохраняет идентификатор прогона; доступ требует работающего приложения и прав пользователя. Документ читается самостоятельно без подключения к приложению; интерактивное исследование открывается по ссылке.

Мнение ИИ в карточке задания присутствует отдельным требованием; его нельзя молча вычеркнуть ради минимального экрана. Для него предлагается блок после проверок: наблюдение, основание, ссылки на связанные результаты. ИИ не меняет PASS / FAIL. Видны состояния ожидания, готовности и ошибки; недоступность модели не скрывает готовые результаты расчёта. Приоритет реализации этого блока нужно согласовать с капитаном, если времени не хватает.

## 11. Состояния и адаптация

Предусмотрены пустой список прогонов, неверная конфигурация, ожидание обработки, ошибка процедуры, готовый отчёт без различий, фильтр без результатов и ошибка загрузки. Сообщения предлагают конкретное действие: выбрать датасет, открыть код, сбросить фильтр, повторить запрос.

Основной ориентир — ноутбук 1366 × 768. Шапка около 56 px, навигация сворачивается, большие таблицы прокручиваются внутри рабочей области. Заголовки и ключевые колонки закреплены. На узких экранах показатели располагаются в два ряда, настройки раскладки уходят в выдвижную панель. Сравнение не сжимается до нечитаемых колонок.

Все действия доступны с клавиатуры, фокус видим, у иконок есть подписи. Панель заявки закрывается Escape и возвращает фокус к исходной строке. Наведение может давать подсказку, но не быть единственным способом прочитать значение.

## 12. Зависимости от API и порядок реализации

Текущий `docs/api.md` покрывает загрузку пары файлов, итог, список заявок, детали, причины, разрезы и CSV. Для описанного проекта не хватает согласованных контрактов:

- конфигурации, датасеты и повторные запуски;
- процедуры, источники Python-кода, параметры и исполнение;
- этапы, прогресс, журнал и связь с кодом;
- факты сводной, измерения, корректные показатели и переходы к выборкам;
- единый отчёт проверок, уверенность и применение новой проверки;
- самостоятельный HTML-отчёт;
- доступ пользователей к своим конфигурациям и запускам;
- получение и состояние мнения ИИ.

Это список необходимых договорённостей, а не утверждённые новые ручки. API в рамках дизайн-проекта не изменён. Перед интеграцией нужно обновить `docs/api.md` совместно с бэком и отдельно проверить определения всех счётчиков.

Порядок сборки: каркас и настройка → рабочая область и запуск → журнал → итоговые показатели → изменяемая сводная и детализация → проверки и добавление новой → HTML и мнение ИИ → проверка полного сценария в браузере. Это порядок работы, а не разрешение исключить поздние пункты ТЗ.

Критерий готовности дизайна в реализации — воспроизводимый путь: настроить прогон, запустить, открыть код из журнала, получить итоги, поменять раскладку, дойти до конкретного атрибута, добавить проверку, увидеть её в общем отчёте, скачать HTML и вернуться из него в приложение. Включить проверку разделения пользовательских запусков и отзывчивости интерфейса во время расчёта.

Сам дизайн-проект — текстовый документ. Рабочий интерфейс и браузерная проверка в эту задачу не входили.
