# Замеры и ускорение (E11)

**Одной фразой для защиты:** узким местом было первое открытие отчёта: сводная заново читала с диска витрину
сравнения (291 тыс. строк, 45 МБ) и приводила её к типам — ~0,5–0,7 с. Сделали прогрев кэшей отчёта в конце
запуска (и в фоне при открытии страницы запуска после перезапуска сервера). Теперь первое открытие сводной
занимает ~30 мс вместо ~0,5 с, переход к заявке — ~15 мс вместо ~0,2 с.

## Как мерили

```bash
cd backend
.venv/Scripts/python -m pipeline.tools.bench <папка_датасета>      # Linux/macOS: .venv/bin/python
```

Скрипт `backend/pipeline/tools/bench.py`:
1. по очереди прогоняет шаги конвейера на датасете (как этапы запуска) и меряет каждый;
2. поднимает приложение через `TestClient` на готовом результате и дважды вызывает каждую ручку отчёта.
   «Без прогрева» — перед **каждой** ручкой кэши приложения пустые (так было сразу после конца запуска и после
   перезапуска сервера). «После прогрева» — сначала `warmup.warm()`, как теперь делает приложение.
   Файловый кэш ОС при этом горячий (файлы только что записаны), так что реальный первый клик после перезагрузки
   машины без прогрева был бы ещё медленнее.

Датасет организаторов `RUN-20260827-0001`: 2002 заявки × 2 среза = 4004 JSON, 291 151 строка витрины.
Числа ниже — одного прогона; от прогона к прогону они гуляют на 10–30 %, порядок не меняется.

## Машина

- Ноутбук Егора: Windows 11 (10.0.26200), Intel Core 11-го поколения (Family 6 Model 141), 12 логических ядер,
  15,8 ГБ памяти, Python 3.12.6, pandas 3.1.1. Без Docker.

Без этапа `checks` (зависит от того, какие проверки подключены) и без прогрева (0,7 с). Конфиг разбора — как у
запуска по умолчанию: `ignore_paths` = технические поля из `manifest.json`.

Планка ТЗ «приведение и сравнение всего датасета» — отлично при ≤ 30 с. Мы примерно в 3 раза быстрее планки, поэтому
конвейер не трогали (в задаче: «не оптимизируй то, что и так укладывается в „отлично“»). Если понадобится: самый
долгий шаг — `compare` (слияние двух таблиц по ключу), затем `normalize` двух срезов, которые идут один за
другим (их можно распараллелить по процессам).

Сам прогрев — **0,7 с**, один раз на запуск, до статуса `ready`: запуск на эти 0,7 с дольше выглядит `running`
(все этапы уже `ready`), зато первый клик по отчёту не ждёт диска.

Планки ТЗ: открытие сводной — отлично при ≤ 0,5 с (было 0,5–0,7 с, на грани; стало 0,03 с); смена раскладки,
фильтр, переход к заявке — отлично при ≤ 0,3 с (были 0,2 с, стало ≤ 0,03 с); повторное открытие — «мгновенно»
(повторный вызов из кэша, 2–30 мс).

## Где было узкое место

Профиль первого вызова `/facts` (`cProfile`): чтение `comparison.csv` — 0,22 с, приведение колонок к категориям
(`astype`) — 0,29 с, остальное — слияние с `segments.csv` и группировка. `/apps/{id}/attributes` читал тот же
файл ещё раз (свой кэш) — 0,2 с. Повторные вызовы уже брали готовое из `lru_cache`, медленным был только первый.

## Что сделали

`backend/app/services/warmup.py` — `warm(run_dir)` загружает в кэш всё, что читают ручки отчёта (заявки,
слой разрезов, атрибуты, база сводной):
- `services/runs.py` вызывает его после последнего этапа, **до** статуса `ready`;
- `GET /runs/{id}` готового запуска запускает его в фоне — после перезапуска сервера кэши пустые, а страницу
  запуска открывают раньше сводной. Один раз на запуск за жизнь процесса.

Формат CSV витрины не меняли, новых зависимостей нет. Эталонные числа (2002 / 385 / 273 / 112) те же, все тесты
бэка зелёные, отмена посреди `normalize` работает (`test_cancel_stops_run`).

Сбой прогрева запуск не портит: ошибка уходит в лог сервера, запуск всё равно `ready`, ручка посчитает сама
(`test_warm_failure_keeps_run_ready`). «Стоп» во время прогрева работает: запуск остаётся остановленным.

**Цена:** память — около **41 МБ на запуск** (`tracemalloc` в `bench.py`). Большие таблицы (атрибуты и база
сводной) кэш держит для 4 последних запусков, список заявок и слой разрезов — для 16 (размеры `lru_cache` в
`results.py` и `facts.py` не меняли). Прогрев загружает заранее то, что первый же клик загрузил бы сам; но фоновый
прогрев при открытии старого запуска может вытеснить из кэша один из 4 свежих. Каждый запуск греется в фоне один
раз за жизнь процесса.

**Что не сделали:** хранить витрину в `parquet` рядом с CSV — нужна новая зависимость (`pyarrow`), а прогрев уже
убрал задержку с пути пользователя.
