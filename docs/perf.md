# Замеры и ускорение (E11)

> Исторический эксперимент E11: его 10,4 с — частичный конвейер до добавления UNION,
> без проверок и прогрева. Это не полное время финального приложения.
> Актуальный контрольный замер `final` / `33ad03d` приведён в конце этого файла
> и в [пояснительной записке](explanatory-note.md#6-измерения-и-проверки).

**Одной фразой для защиты:** узким местом было первое открытие отчёта: сводная заново читала с диска витрину
сравнения (291 тыс. строк, 45 МБ) и приводила её к типам — ~0,5–0,7 с. Сделали прогрев кэшей отчёта в конце
запуска (и в фоне при открытии страницы запуска после перезапуска сервера). В том эксперименте первый вызов горизонтальной сводной
занимал ~30 мс вместо ~0,5 с, переход к заявке — ~15 мс вместо ~0,2 с.
Это время API на прогретом результате, без браузерного рендера; на новый вертикальный слой оно не переносится.

## Как мерили

```bash
cd backend
.venv/Scripts/python -m pipeline.tools.bench <папка_датасета>      # Linux/macOS: .venv/bin/python
```

Скрипт `backend/pipeline/tools/bench.py`:
1. по очереди измеряет приведение, сравнение, разрезы и итоги; он не воспроизводит весь актуальный запуск: UNION и проверки в этот замер не входят;
2. поднимает приложение через `TestClient` на готовом результате и дважды вызывает каждую ручку отчёта.
   «Без прогрева» — перед **каждой** ручкой кэши приложения пустые (так было сразу после конца запуска и после
   перезапуска сервера). «После прогрева» — сначала `warmup.warm()`, как теперь делает приложение.
   Файловый кэш ОС при этом горячий (файлы только что записаны), так что реальный первый клик после перезагрузки
   машины без прогрева был бы ещё медленнее.

Датасет организаторов `RUN-20260827-0001`: 2002 заявки × 2 среза = 4004 JSON, 291 151 строка витрины.
Числа ниже — одного прогона; от прогона к прогону они гуляют на 10–30 %, порядок не меняется.

## Машина

- Ноутбук Егора: Windows 11 (10.0.26200), Intel Core 11-го поколения (Family 6 Model 141), 12 логических ядер,
  15,8 ГБ памяти, Python 3.12.6, pandas 3.1.1. Без Docker.

Без построения UNION, этапа `checks` (зависит от подключённых проверок) и прогрева (0,7 с). Конфиг разбора — как у
запуска по умолчанию: `ignore_paths` = технические поля из `manifest.json`.

Планка ТЗ «приведение и сравнение всего датасета» — отлично при ≤ 30 с. Исторический замер укладывался в неё;
он не подтверждает тот же запас для финального конвейера с UNION. Если понадобится ускорение: самый
долгий шаг — `compare` (слияние двух таблиц по ключу), затем `normalize` двух срезов, которые идут один за
другим (их можно распараллелить по процессам).

## Ручки отчёта: до и после

| Ручка | Что в интерфейсе | До: первый вызов, мс | После: первый вызов, мс | Повторный, мс |
|---|---|---:|---:|---:|
| `/summary` | обзор | 4 | 3 | 2 |
| `/apps?size=500` | список заявок | 20 | 16 | 16 |
| `/apps?decision_change=approve_to_reject` | фильтр | 9 | 6 | 5 |
| `/apps/{id}/attributes` | переход к заявке | **197** | **15** | 6 |
| `/facts?dims=PATH,CHANGE_TYPE` | открытие сводной | **512** | **29** | 57 |
| `/facts?dims=ARRAY_KEY_1` | смена раскладки | **486** | **17** | 22 |
| `/report` | HTML-отчёт | 18 | 4 | 5 |

Сам прогрев — **0,7 с**, один раз на запуск, до статуса `ready`: запуск на эти 0,7 с дольше выглядит `running`
(все этапы уже `ready`), зато первый клик по отчёту не ждёт диска.

Планки ТЗ: открытие сводной — отлично при ≤ 0,5 с (было 0,5–0,7 с, на грани; стало 0,03 с); смена раскладки,
фильтр, переход к заявке — отлично при ≤ 0,3 с (были 0,2 с, стало ≤ 0,03 с); повторное открытие — «мгновенно»
(повторный вызов из кэша, 2–30 мс).

## Где было узкое место

Профиль первого вызова `/facts` (`cProfile`): чтение `comparison.csv` — 0,22 с, приведение колонок к категориям
(`astype`) — 0,29 с, остальное — слияние с `segments.csv` и группировка. `/apps/{id}/attributes` читал тот же
файл ещё раз (свой кэш) — 0,2 с. Повторные вызовы уже брали готовое из `lru_cache`, медленным был только первый.

## Что сделали

`backend/app/services/warmup.py` — `warm(run_dir)` загружает в кэш всё, что читают ручки отчёта (заявки,
слой разрезов, атрибуты, база сводной):
- `services/runs.py` вызывает его после последнего этапа, **до** статуса `ready`;
- `GET /runs/{id}` готового запуска запускает его в фоне — после перезапуска сервера кэши пустые, а страницу
  запуска открывают раньше сводной. Один раз на запуск за жизнь процесса.

Формат CSV витрины не меняли, новых зависимостей нет. Эталонные числа (2002 / 385 / 273 / 112) те же, все тесты
бэка зелёные, отмена посреди `normalize` работает (`test_cancel_stops_run`).

Сбой прогрева запуск не портит: ошибка уходит в лог сервера, запуск всё равно `ready`, ручка посчитает сама
(`test_warm_failure_keeps_run_ready`). «Стоп» во время прогрева работает: запуск остаётся остановленным.

**Цена в этом эксперименте:** около **41 МБ** по `tracemalloc` в `bench.py` — оценка измеренных кешей Python,
не RSS всего приложения и не замер новой вертикальной витрины. Большие таблицы (атрибуты и база
сводной) кеш держит на 4 записи, список заявок и слой разрезов — на 16 записей (размеры `lru_cache` в
`results.py` и `facts.py` не меняли). Прогрев загружает заранее то, что первый же клик загрузил бы сам; но фоновый
прогрев при открытии старого запуска может вытеснить из кэша один из 4 свежих. Каждый запуск греется в фоне один
раз за жизнь процесса.

**Что не сделали:** хранить витрину в `parquet` рядом с CSV — нужна новая зависимость (`pyarrow`), а прогрев уже
убрал задержку с пути пользователя.


## Контрольный замер финальной версии, 7 ноября 2026

Код `33ad03d`, основной набор 2002 × 2 ответа, стандартные процедуры и пять проверок.
Прямой вызов реальных функций этапов с `perf_counter`, без HTTP, браузера и облачного ИИ.
Windows 11 (26300), Intel64 Family 6 Model 186, 12 логических ядер, 31,6 ГБ,
Python 3.14.7, pandas 3.1.1; Docker не использовался. Это один замер, не распределение задержек.

| Операция | Время, с |
|---|---:|
| Приведение обоих срезов | 14,09 |
| Сравнение + UNION | 14,33 |
| Разрезы + итоги | 2,72 |
| Пять проверок | 13,96 |
| Прогрев | 1,16 |

Приведение + сравнение с UNION: **28,42 с**. Результат: 291 151 строка сравнения,
575 072 строки UNION; 34 строки проверок, 1 PASS / 33 FAIL, ошибок исполнения нет.
Вызовы сервиса сводной: горизонтальный после прогрева — 40 мс, первый вертикальный — 1450 мс,
повторный вертикальный — 22 мс. Вертикальная база загружается лениво и не прогрета основным `warm()`.
Эти времена не подтверждают время полного пользовательского действия в браузере или скорость другой машины.

[Машиночитаемая сводка замера и контрольной сверки](measurements/final-2026-11-07.json)
содержит только окружение и агрегаты, без исходных ответов и идентификаторов заявок.
Для повторения бизнес-результата используйте [инструкцию запуска](../README.md#7-инструкция-по-запуску)
и те же исходные проверки. Для времени приложения измеряйте новый запуск до `ready`;
для отдельных этапов используйте времена журнала, учитывая, что прогрев идёт после последнего этапа.
HTTP-ожидание, накладные расходы менеджера и округление журнала отличаются от прямого замера функций.
