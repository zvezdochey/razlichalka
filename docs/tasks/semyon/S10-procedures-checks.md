# S10. (после MVP) Процедуры, проверки и этап `checks`

**Кто:** Семён · **Ветка:** `semyon/checks` · **Папка:** `backend/app/` · **Зависит от:** S5, S6; E8 слит

**Запуск в новом чате:** «Выполни задачу из `docs/tasks/semyon/S10-procedures-checks.md`. Сначала прочитай `AGENTS.md`, `docs/api.md` (п. 3, 4, 10) и `docs/tasks/CONTRACTS.md`.»

## Зачем
Пользователь пишет свои проверки на Python, подключает к конфигурации и видит результат в общей таблице PASS/FAIL (требование ТЗ; на защите могут подложить свою проверку).

## Что сделать
1. **Процедуры** (п. 3): `app/routers/procedures.py`, хранение через `store.py`.
   - Встроенные (`builtin: true`) создаются при старте: `builtin_normalize`, `builtin_aggregate` и 5 проверок организаторов. Файлы проверок скопируй в `backend/checks/` (это учебные примеры организаторов; перед коммитом уточни у капитана/команды, можно ли — иначе читай из `ПАКЕТ/…/checks/` по пути из `DATASETS`-соседнего тома и не коммить);
   - `GET /api/procedures?kind=`, `POST` (201, при плохом коде → `bad_code` с строкой), `POST /validate`, `PUT`, `DELETE` (встроенные → `conflict` 409). Валидацию кода делает `pipeline.checks_runner.validate_check_code` (E8).
2. **Этап `checks`** вместо пропуска из S5: загрузить выбранные проверки конфигурации (`config.checks`), собрать `Mart` по `comparison.csv`/`segments.csv`, `run_checks`, записать `checks.csv`. В журнал этапа — по строке на проверку; ошибка пользовательского кода — **не валит запуск**, а даёт отдельную строку с `error` в логе (см. `frontend/DESIGN.md`: «ошибка выполнения» ≠ FAIL).
3. **Результат** `GET /api/runs/{id}/checks?result=&page=&size=` (п. 10.1): колонки `CHECK` → поля API (`check_id`, `check_name`, `source`, `argument`, `numbers` = `"CNT / TOTAL"`, `metric`, `result`, `apps_ref`, `faint = CONFIDENCE==LOW`). `apps_ref` — как в S9 (ссылка на список `APP_IDS`).
4. Блок «Проверки» в HTML-отчёте (S7) — реальная таблица, FAIL с `LOW` бледно.
5. Для `summary.json` добавить `checks_fail` (число строк FAIL) — нужно карточке «Проверки с FAIL» на обзоре; впиши в `docs/api.md` п. 7.1 и скажи Сане.

## Безопасность
Пользовательский код выполняется в отдельном процессе с таймаутом (E8). В Docker контейнер уже без root. Не давай коду доступа к `DATA_DIR/configs` и переменным окружения с секретами.

## Тесты
Создание/валидация/удаление процедуры, встроенную не удалить, запуск с 5 встроенными проверками до `ready`, сломанная пользовательская проверка не роняет запуск, `GET /checks?result=FAIL`.

## Готово, когда
Добавленная через API проверка появляется в таблице после нового запуска; 5 проверок организаторов работают как есть.
