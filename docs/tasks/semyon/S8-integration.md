## Зачем
Когда все части слиты — убедиться, что прототип проходит весь путь на настоящих данных, и привести цифры и доки в порядок. Это «минимально рабочий прототип».

## Что сделать
1. Чистый старт: клонировать репозиторий в пустую папку, положить датасет, `docker compose up --build` — поднялось.
2. Агентом `browser-tester` пройти сценарий: открыть фронт → «Новый прогон» → выбрать `RUN-20260827-0001` → запустить → смотреть журнал этапов → обзор с четырьмя счётчиками → таблица заявок → фильтр `approve_to_reject` → открыть заявку → атрибуты → «Скачать HTML». Консоль браузера без ошибок. Скриншоты — в описание PR.
3. Агентом `api-tester` сверить каждую MVP-ручку с `docs/api.md`.
4. Сверить цифры: `applications=2002`, `decision_changed=385`, `decision_changes` 1617/273/112/0. Если `applications_changed` и `attributes` отличаются от примера в `docs/api.md` п. 7.1 — **обновить пример реальными числами** и убрать оговорку «ориентир» (с согласия Егора, что нормализация по ключам правильная; подтвердить: дублей ключей нет, `ATTRIBUTE_NEW`/`LOST` объяснимы составом атрибутов).
5. Замерить время запуска, записать в README («полный прогон занимает ~N секунд»).
6. Нашёл баг — заводи маленькую задачу владельцу (Егор/Саня), не чини молча чужую папку.
7. README: раздел «Как запустить» актуален, есть раздел «Как это работает» — 5–8 строк про 4 этапа и что где лежит (для защиты).
8. Подготовить демо-данные заранее: один готовый запуск, чтобы на защите не ждать расчёта.
