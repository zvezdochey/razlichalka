## Зачем
В ТЗ, раздел «Что не будет принято»: «Разбор, зашитый под этот датасет. Имена полей и пути в коде приложения,
а не в процедуре пользователя: на следующем прогоне такое решение придётся переписывать». На защите
организаторы могут подложить свою процедуру или другой ответ СПР.

Сейчас под датасет зашиты:
- `pipeline/array_rules.py` → `DEFAULT_ARRAY_RULES`: пути девяти массивов **и их ключи**;
- `pipeline/segments.py`: откуда брать решение, продукты, модель PD, порог, причину отказа, скоры
  (`decisionResult`, `product_trials`, …).

Код разбора (`flatten`, `compare`) — общий и ничего не знает про СПР. Так и должно остаться.

## Что сделать

### 1. Процедуры по умолчанию — файлы, а не код
Новая папка `backend/procedures/` — это «встроенные процедуры» из `docs/api.md` п. 3:

```
backend/procedures/
  builtin_normalize.py    # ARRAY_RULES = {...}   — правила массивов (режим + ключ)
  builtin_segments.py     # FIELD_MAP = {...}     — карта полей слоя разрезов
```

Формат — обычный Python-модуль с одной переменной-словарём (не JSON): его можно открыть «как код этапа»
из журнала (шаг 2 демо) и прочитать человеку. Код внутри — только данные, без логики. Вверху каждого файла —
комментарий на русском: что это, откуда правила (`ФОРМАТ_ОТВЕТА.md`, «Массивы: девять штук»), как поменять.

Загрузка — `pipeline/procedures.py`: `load_builtin(name) -> dict` через `importlib` по пути файла (не через
`import backend.procedures…`, чтобы `pipeline` не зависел от раскладки пакета). Путь к папке приходит аргументом
или из `PROCEDURES_DIR` с умолчанием `backend/procedures` — читает `app/settings.py`, как и остальные пути.

### 2. Правила массивов
- `DEFAULT_ARRAY_RULES` из `array_rules.py` переезжает в `builtin_normalize.py`. В `array_rules.py` остаётся
  только логика (`merge_array_rules` и т. п.).
- Новое поле конфигурации **`array_rules`**: `{ "<путь массива>": { "mode": "key", "key": ["product_id"] } }` —
  перекрывает правило целиком, можно добавить правило для нового массива.
- Старое `array_modes` продолжает работать (меняет только режим) — тесты и фронт не ломаем.
- Порядок: правила процедуры → `array_rules` конфигурации → `array_modes` конфигурации.

### 3. Карта полей слоя разрезов
- В `builtin_segments.py` — `FIELD_MAP`: для каждого поля `segments.csv` откуда оно берётся
  (`"DECISION": "decisionResult.decision"`, `"PRODUCTS": "decisionResult.product_trials[].product_id"`, …).
  Нестандартные вычисления (верхний оффер, «продукт с наименьшим id, если выдачи нет») оставь функциями в
  `segments.py`, но **пути** они берут из карты.
- `build_segments(dataset_dir, out_csv, field_map=None, ...)` — без карты берёт встроенную. Сигнатуру в
  `CONTRACTS.md` §4 обнови.
- Эта же карта нужна Илье в I3 (карточка заявки) — сделай для неё публичную функцию `read_field(doc, name, field_map)`
  или аналог и скажи ему.

### 4. Код этапа в журнале
`CODE_REFS` в `app/services/stages.py` сейчас указывают на `backend/pipeline/normalize.py`. После этой задачи
«код этапа» `normalize` — это `backend/procedures/builtin_normalize.py`. Поправлять `stages.py` — Семёну (это
`app/`), передай ему пути. Ручку, которая отдаёт текст файла, Семён делает в S10.
