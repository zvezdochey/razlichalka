## Зачем
Шаг 4 демо: «Откройте сводную таблицу — раскладка по атрибутам и типам изменения». По ТЗ сводная —
это **инструмент**: раскладку меняет пользователь. Ручка `/facts` её кормит, а вкладку на фронте
делаешь тоже ты (I2), поэтому формат ответа удобен в первую очередь тебе самому.

Требование ТЗ к скорости: открытие сводной ≤ 2 с, смена раскладки и фильтр ≤ 1 с (хорошо — ≤ 0,3 с).
Здесь нас и будут сравнивать с другими командами.

## Что сделать

### 1. База фактов — один раз на запуск
- В `services/` новый модуль `facts.py`. Функция `_facts_base(run_dir)` с `@lru_cache` (как `_apps` в `results.py`):
  читает `comparison.csv` (~290 тыс. строк) и `segments.csv`, склеивает по `APP_ID` (`merge` left), возвращает `DataFrame`.
- Текстовые колонки переводи в `category` — `groupby` по ним в разы быстрее и памяти меньше.
- `DIFF_FLAG` → `int`. Добавь производную колонку **`ARRAY_KEY_1`** — первый ключ из `ARRAY_KEY` (до первого `|`).
  Для строк продуктов это `product_id`, и так получается разрез «по продуктам» без зашитых в код путей.
- Замерь время первого и повторного вызова на настоящем датасете, запиши в PR.

### 2. `GET /api/runs/{id}/facts` (п. 7.2)
- `dims` — через запятую, 1–3 поля. Разрешены все колонки базы (`PATH`, `CHANGE_TYPE`, `DIFF_FLAG`, `PREFIX`,
  `CLASS`, `KEY`, `ARRAY_KEY_1`, поля `segments.csv`, после E10 — `CHANGE_SOURCE`). Неизвестное поле → 400
  (код — тот, что Семён зафиксирует в S11 для невалидного запроса; до этого — `bad_file`, как у `/apps`).
- `filter=поле:значение;поле:значение` — строгое равенство, поля из того же списка. Несколько значений одного
  поля через `,` (`CHANGE_TYPE:VALUE_CHANGED,ATTRIBUTE_NEW`) — это OR.
- `measure=counts` (число строк) | `counts_distinct_apps` (уникальные `APP_ID`). По умолчанию `counts`.
- Сортировка групп — по убыванию показателя. Групп по `PATH × ARRAY_KEY_1` может быть десятки тысяч, поэтому
  **`limit`** (по умолчанию 1000, максимум 5000) и в ответе **`total_groups`**. Это дополнение к договору —
  впиши его в `docs/api.md` п. 7.2 **до** кода.
- Пустые значения измерений — `null`.
- Запуск не `ready` → 409 `not_ready`, чужой/неизвестный → 404 (как в остальных ручках результатов).

### 3. `app_ids_ref` и `GET /api/runs/{id}/facts/{ref}/apps` (п. 7.3)
- `ref` = `f_` + первые 12 символов `sha1` от `run_id + dims + filter + значения группы`.
- Храни **не список id, а определение группы** (фильтр + значения измерений) в `facts_refs.json` в папке запуска.
  Пиши атомарно и под `threading.Lock` (как `run.json` в `store.py`): ручки зовут параллельно.
- `/facts/{ref}/apps?page=&size=` применяет определение к базе, отдаёт уникальные `APP_ID` по возрастанию, `total`.
  Неизвестный `ref` → 404.
- **Сделай это одной функцией `make_apps_ref(run_dir, filters) -> str`**: Семёну она нужна в S10 для `apps_ref` у
  проверок (там готовый список `APP_IDS`, поэтому функция должна уметь хранить и явный список id). Договорись с ним.

### 4. `GET /api/runs/{id}/export.csv` (п. 13)
- Те же фильтры, что у `GET /apps` (`decision_change`, `has_attr_change`, `search`, `sort`) — **переиспользуй**
  функцию фильтрации из `results.py`, не копируй.
- Все строки, без пагинации. `;` и `utf-8-sig` (через `pipeline/csvio.py`), чтобы открывался в Excel двойным кликом.
- `Content-Type: text/csv; charset=utf-8`, `Content-Disposition: attachment; filename="apps-<run_id>.csv"`.

## Тесты (`backend/tests/api/test_facts.py`, фикстура `run_mini`)
- `dims=CHANGE_TYPE`: сумма `counts` = число строк `comparison.csv`; сходится с ручным `groupby` в тесте.
- `filter=DIFF_FLAG:1` + `counts_distinct_apps` сходится с ручным подсчётом.
- `app_ids_ref` из строки ведёт ровно на заявки этой группы.
- неизвестное измерение → 400; неготовый запуск → 409.
- `export.csv` читается `pandas.read_csv(sep=";", encoding="utf-8-sig")`, фильтр `decision_change` работает.
