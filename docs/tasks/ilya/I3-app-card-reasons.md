## Зачем
Сценарий 3 ТЗ — «Почему у этих заявок изменилось решение?» и цель задания «что изменилось, у кого и **из-за чего**».
Таблица атрибутов (F7) показывает *что* изменилось, карточка — *почему*. На «Обзоре» блок «Что ломает решение»
отвечает на сценарий 1 «Стоит ли бояться?».

## Что сделать

### 1. `GET /api/runs/{id}/apps/{app_id}` (п. 8.2)
- Читает два исходных JSON этой заявки из датасета запуска (BEFORE и AFTER). Файлы искать через
  `pipeline/dataset.py` (`list_source_files` / имя файла = `APP_ID`), путь к датасету — из `run.json`.
- Собирает `before` / `after`: `decision`, `offers`, `products[]` (`product_id`, `decision`, `reject_reason`,
  `reject_reason_code`, `pd_model`, `pd`, `cutoff {name, value}`, `rules [{name, hit}]`).
- **Пути не зашивай в `app/`.** Егор в E9 выносит «карту полей» (откуда брать решение, продукты, модель, порог)
  в файл процедуры. Читай поля через неё. Если E9 ещё не слита — положи карту в один словарь в начале модуля
  с комментарием `# TODO: перенести в карту полей E9` и скажи Егору.
- Ключ оффера — пара `product_id` + `type` (в примере `api.md` у `15210` два оффера).
- Нет заявки → 404; запуск не `ready` → 409.

### 2. `reasons` в карточке — простые правила, по продукту
Сравнивай продукт BEFORE с тем же `product_id` в AFTER:

| Что видно | `source` | `confidence` | Текст |
|---|---|---|---|
| стоп-фактор `hit=true` в одном срезе и `false`/нет в другом | `rule` | `high` | «Стоп-фактор AGELOW@21 сработал в BEFORE, в AFTER — нет» |
| сменилось имя или значение порога `cutOff` | `cutoff` | `high` | «Порог MFO_ZAIMER_2026 → MFO_ZAIMER_2026_MID (0.55 → 0.62)» |
| сменилась модель `pd_model` | `score` | `high` | «Модель PD сменилась: V1 → V2» |
| модель та же, `pd` переехал через порог | `score` | `high` | «PD 0.494 → 0.694 при пороге 0.62» |
| продукт есть только в одном срезе | `product` | `high` | «Продукт 751 появился в AFTER» |
| решение сменилось, а входные данные заявки различаются (после E10: `CHANGE_SOURCE` = `data`/`both`) | `data` | `low` | «Возможная причина — изменились ответы внешних источников» |
| ничего не нашли | `unknown` | `low` | «Причина не найдена в решающих полях» |

Где это догадка — формулировка «Возможная причина…». Новый `source: data` впиши в словарь `api.md` п. 8.2.

### 3. `GET /api/runs/{id}/reasons` (п. 9)
- Берём заявки со сменой решения на `reject` (`decision_change = approve_to_reject`).
- Считаем строки продуктов с причиной отказа в AFTER, группируем по `REJECT_REASON` + имени правила/порога
  (`CUTOFF:MFO_ZAIMER_2026_LOW`, `HARDCHECK:DOCS_EXPIRED`), `source` = `cutoff` / `rule` по префиксу.
- `share` — доля от всех таких строк продуктов (в `api.md` п. 9 их 645 — сверь).
- **`unexplained`** — теперь посчитай: число заявок со сменой на `reject`, у которых не нашлось ни одной причины.
  Убери из `api.md` фразу «пока `null`».
- Каждой причине добавь `app_ids_ref` через `make_apps_ref` из I1 — тогда с «Обзора» можно провалиться в заявки.
  Дополнение — в `api.md` п. 9.
- После E10 добавь в ответ `by_source: { "logic": N, "data": N, "both": N }` — это готовая фраза для демо
  «из 385 смен решения N — из-за входных данных».
