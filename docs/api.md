# API: договорённость между бэком и фронтом

Это «розетка и вилка». Бэк отдаёт ровно такие ответы, фронт рассчитывает ровно на них.
Хочешь поменять формат — сначала договорись со второй стороной и поправь этот файл.

Версия 2 (6 ноября). Переписана под ТЗ: на вход — готовый датасет прогона, а не два файла.
Данные: `ПАКЕТ/ЗАДАНИЕ/data/RUN-20260827-0001/` — два среза по 2002 JSON-файла.

Примеры ниже взяты из этого датасета (посчитано скриптом по файлам), кроме мест, где явно написано «форма».

**Статус: MVP.** Обязательно для показа: 5.1–5.2 (запуск и статус), 6 (этапы), 7.1 (итоги), 7.4 (список заявок), 8.1 (атрибуты заявки), 11 (отчёт). Остальное — после MVP: процедуры и проверки (3, 10), конфигурации (4), факты (7.2–7.3), карточка заявки (8.2), причины (9), мнение ИИ (12), экспорт (13).

Адрес бэка: `http://localhost:8000`. Все ручки начинаются с `/api`.
Пользователь пока не авторизуется: передаём заголовок `X-User: <имя>`. Конфигурации и запуски принадлежат этому пользователю.

---

## Главная идея

1. Пользователь выбирает датасет, процедуры и проверки и **сохраняет конфигурацию**.
2. По конфигурации создаётся **запуск** (`run`). Бэк обрабатывает его в фоне.
3. Фронт опрашивает статус и этапы. Когда запуск `ready`, фронт открывает отчёт.
4. Запуск не пропадает после перезагрузки страницы: фронт берёт его по `id`.

Частичные результаты не показываем: витрину, факты и отчёт отдаём только у запуска в статусе `ready`.

## Общие словари

**Срез** (`source`): `BEFORE` (MASTER, прод) и `AFTER` (BETA, изменение).

**Решение** (`decision`): `approve`, `reject`, `other`.
Бэк сам переводит `APPROVE`/`REJECT` из данных (и любые другие написания) в эти значения. В датасете встречаются только `APPROVE` и `REJECT`.

**Решение изменилось** (`decision_change`):

| Значение | Что значит |
|---|---|
| `same` | решение то же |
| `approve_to_reject` | было approve → стало reject |
| `reject_to_approve` | было reject → стало approve |
| `decision_other` | решение изменилось иначе (например, на `other`); в датасете таких нет |

**Изменение атрибута** (`change_type`) — из ТЗ, ровно четыре значения:

| Значение | Что значит |
|---|---|
| `SAME` | атрибут есть в обоих срезах, значения совпадают |
| `VALUE_CHANGED` | атрибут есть в обоих срезах, значения разные |
| `ATTRIBUTE_NEW` | атрибута нет в BEFORE, есть в AFTER |
| `ATTRIBUTE_LOST` | атрибут есть в BEFORE, нет в AFTER |

**Откуда смена** (`change_source`) — сценарий 4 ТЗ: «это из-за изменения логики или из-за входных данных?»:

| Значение | Что значит |
|---|---|
| `logic` | вход тот же, различия только в том, что посчитала СПР — изменение из-за новой версии |
| `data` | у заявки другой вход: есть различие в данных заявки (`appData`) или в ответах внешних источников (`ext_data[]`). Для проверки логики это ложная тревога |
| `both` | вход другой, и решение поменялось сильнее, чем объясняет вход. **Пока не считаем**: честного критерия нет, а на датасете у всех заявок с другим входом смена решения им и объясняется. Значение зарезервировано, сейчас всегда `0` |
| `none` | различий нет совсем. У заявки со сменой решения так быть не должно (бэк пишет предупреждение в журнал этапа) |

Что считается входом — список префиксов `INPUT_PREFIXES` в процедуре `backend/procedures/builtin_segments.py` (сейчас `appData`, `ext_data`). `characteristics` — уже этап 1 СПР (готовые скоры), поэтому это логика. Технические поля из `ignore_paths` не считаются: их нет в витрине.

**Статус** (`status`) у датасета, конфигурации этапа и запуска: `pending`, `running`, `ready`, `error`.

## 2. Датасеты

### 2.1. Список доступных датасетов

`GET /api/datasets`

```json
{
  "datasets": [
    {
      "id": "RUN-20260827-0001",
      "applications": 2002,
      "sources": { "BEFORE": "MASTER", "AFTER": "BETA" },
      "technical_fields": ["appData.request_id", "appData.createDateTime"]
    }
  ]
}
```

Датасеты лежат на сервере (папка `DATASETS_DIR`, только чтение) или появляются через загрузку (п. 2.2, папка `DATA_DIR/uploads`). В списке они выглядят одинаково. В режиме заглушки, если доступных датасетов нет, API предлагает демонстрационный `RUN-MINI`.

### 2.2. Загрузка датасета

`POST /api/datasets/upload` — `multipart/form-data`

| Поле | Обязательное | Что это |
|---|---|---|
| `before` | да | файлы среза «до». Поле можно повторять: один файл на заявку или один архив |
| `after` | да | файлы среза «после», так же |
| `before_label`, `after_label` | нет | названия срезов (как `MASTER` / `BETA`). По умолчанию `BEFORE` / `AFTER` |
| `technical_fields` | нет | пути, которые различаются у всех заявок по определению (повторяемое поле). Нет поля — бэк находит их сам: пути вне массивов, которые отличаются у **каждой** пары заявок (нужно хотя бы 3 пары) |

Что принимается в `before` / `after`:

| Файл | Как читается |
|---|---|
| `.json` | ответ СПР как у организаторов. Если в файле список, то каждый элемент — отдельная заявка |
| `.xml` | то же дерево в XML. Имя корневого тега не важно, вложенные теги — ключи. Повторяющиеся теги — массив; пути массивов из процедуры «Приведение ответов» остаются массивами и при одном элементе. Текст `123`, `1.5`, `true`, `false` становится числом или булевым, пустой тег — `null` (или `[]`, если это массив). Одиночный тег считается массивом, если путь где-то в датасете — список (в JSON-файле любого среза или повторяющийся тег в XML). Тег `<!DOCTYPE>` и сущности запрещены |
| `.csv` | таблица `path;value` (разделитель `;`, `,` или табуляция). Путь как в витрине: `decisionResult.product_trials[0].rules[1].name`. Нужна колонка `path` и колонка `value`. Если в файле несколько заявок — добавь колонку `application_id`. Значения типизируются как в XML |
| `.zip` | архив с файлами перечисленных форматов (папки внутри можно) |

Идентификатор заявки берётся из `appData.application_id` внутри файла. Если в заявке его нет, имя файла (без расширения) подставляется как `application_id`. Допустимые символы id: буквы, цифры, `_`, `-`, `.`.
Всё приводится к одному виду: бэк пишет обычный датасет (`manifest.json` + по JSON-файлу на заявку), дальше работает тот же расчёт.

Ограничения: файл заявки до 20 МБ, присланный архив до 100 МБ, всего за запрос до 150 МБ (и присланных, и распакованных), не больше 50 000 заявок на срез и 100 000 файлов в запросе.

Ответ `201`:

```json
{
  "dataset": {
    "id": "UP-20261107-120000-a1b2",
    "applications": 2002,
    "sources": { "BEFORE": "MASTER", "AFTER": "BETA" },
    "technical_fields": ["appData.request_id", "appData.createDateTime"]
  },
  "received": {
    "BEFORE": { "applications": 2002, "json": 2002, "xml": 0, "csv": 0 },
    "AFTER":  { "applications": 2002, "json": 0, "xml": 2002, "csv": 0 }
  },
  "applications_only_before": 0,
  "applications_only_after": 0
}
```

Ошибки: `bad_request` — нет `before` или `after`, одинаковые названия срезов, присланный файл слишком большой, расширение не из списка; `bad_file` — содержимое не разобрать, в срезе две заявки с одним id, слишком большой файл внутри архива (в `message` — имя файла и причина). Ничего не сохраняется, если хотя бы один файл плохой.

## 3. Процедуры и проверки (код пользователя)

Каждая процедура — это Python-код, который подчиняется контракту из `ПАКЕТ/ЗАДАНИЕ/docs/СХЕМА_ВИТРИНЫ.md` и `checks/README.md`.
Код может быть **из рабочей области** (`source: "inline"`, текст в поле `code`) или **файлом** на сервере (`source: "file"`, путь в поле `path`).

Виды процедур (`kind`):

| `kind` | Вход | Выход |
|---|---|---|
| `normalize` | JSON одного ответа | строки плоской таблицы (поля витрины) |
| `aggregate` | витрина сравнения | факты `counts` для сводного отчёта |
| `check` | факты и витрина | строки `PASS` / `FAIL` |

### 3.1. Список процедур

`GET /api/procedures?kind=check`

```json
{
  "procedures": [
    { "id": "p_1", "kind": "check", "name": "Approval Rate продукта <10%", "source": "inline", "builtin": false, "updated_at": "2026-11-06T12:00:00Z" },
    { "id": "builtin_attribute_new_loss", "kind": "check", "name": "Изменился состав атрибутов", "source": "file", "path": "checks/check_attribute_new_loss.py", "builtin": true, "updated_at": null }
  ]
}
```

Имена встроенных проверок взяты из `checks/` датасета.

### 3.2. Создать процедуру

`POST /api/procedures`

```json
{ "kind": "check", "name": "Approval Rate продукта <10%", "source": "inline", "code": "def run(mart, params):\n    return []\n\nCHECK = {\"id\": \"my\", \"label\": \"Моя\", \"params\": {}, \"entrypoint\": run}\n" }
```

Или с файлом: `{ "kind": "normalize", "name": "...", "source": "file", "path": "procedures/my_norm.py" }`.

Ответ: объект процедуры (`201`). Если код не проходит проверку контракта, ответ — ошибка `bad_code` (см. «Ошибки»), в `message` — где именно.

### 3.3. Проверить код процедуры без запуска

`POST /api/procedures/validate`

```json
{ "kind": "check", "source": "inline", "code": "def run(mart, params):\n    return []\n\nCHECK = {\"id\": \"my\", \"label\": \"Моя\", \"params\": {}, \"entrypoint\": run}\n" }
```

```json
{ "ok": false, "errors": [ { "line": 3, "message": "Нет возврата PASS/FAIL" } ] }
```

Нужна, чтобы фронт показал ошибки до запуска.

### 3.4. Получить, изменить и удалить

- `GET /api/procedures/{id}` — объект процедуры **и поле `code`**: текст файла (для `source: "file"`) или код из тела (`inline`). Файлы отдаются только из `procedures/` и `checks/`; через `..` и абсолютные пути не выйти (`bad_code`). По этому коду фронт показывает «код этапа» из журнала.
- `PUT /api/procedures/{id}` — то же тело, что при создании. Встроенную изменить нельзя (`409 conflict`).
- `DELETE /api/procedures/{id}` — `204`. Встроенные (`builtin: true`) не удаляются, ответ `409` с кодом `conflict`.

### 3.5. Журнал исполнения процедуры

Запуск каждой процедуры пишет логи по этапам (см. раздел 6). Фронт получает их там же.

## 4. Конфигурации

Конфигурация — это «что запускаем»: датасет, процедуры приведения и сравнения, проверки, пути-исключения и режимы массивов.

### 4.1. Список конфигураций пользователя

`GET /api/configs`

```json
{
  "configs": [
    { "id": "cfg_1", "name": "Прогон на 06.11", "dataset": "RUN-20260827-0001", "updated_at": "2026-11-06T12:00:00Z" }
  ]
}
```

### 4.2. Создать конфигурацию

`POST /api/configs`

```json
{
  "name": "Прогон на 06.11",
  "dataset": "RUN-20260827-0001",
  "normalize": "builtin_normalize",
  "aggregate": "builtin_aggregate",
  "checks": ["builtin_attribute_new_loss", "p_1"],
  "ignore_paths": ["appData.request_id", "appData.createDateTime"],
  "array_modes": { "decisionResult.scoring[].value": "index" },
  "array_rules": { "decisionResult.product_trials[]": { "mode": "key", "key": ["product_id"] } },
  "buckets": { "decisionResult.product_trials[].scoring.pd.value": [0.3, 0.6] }
}
```

- `normalize`, `aggregate` — id процедуры нужного `kind`.
- `checks` — список id проверок (`kind: "check"`).
- `ignore_paths` — пути, которые не сравниваем. Два технических поля — из `manifest.json` датасета (`technical_fields_always_differ`): они различаются у всех 2002 заявок.
- `array_rules` — правило массива по пути целиком: `{ "mode": "key", "key": ["поле", ...] }`, или `{ "mode": "value" }`, или `{ "mode": "index" }`. Перекрывает правило встроенной процедуры `builtin_normalize` (файл `backend/procedures/builtin_normalize.py`) и позволяет добавить правило для нового массива. Необязательно, по умолчанию `{}`. Для `key` нужен непустой `key`. Если массива нет ни в процедуре, ни в `array_rules`/`array_modes`, бэк берёт умолчание, а не падает: список скаляров сопоставляется по значению (если значения не повторяются), иначе — по позиции (`index`). То же, если встроенное правило процедуры не подходит к данным (нет поля ключа) и конфигурация его не переопределила; правило из `array_rules`/`array_modes` при несовпадении по-прежнему даёт `bad_file`. Каждый такой откат записывается предупреждением в журнал этапа `normalize` (список массивов), чтобы сравнение по позиции не случилось молча.
- `array_modes` — только режим массива по пути: `key`, `value`, `index` (ключ остаётся из правила). Для `decisionResult.scoring[].value` режим `index` (вектор модели, позиция значима). Полный список массивов и их ключей — в `ФОРМАТ_ОТВЕТА.md` и в `builtin_normalize.py`.
- Порядок перекрытия правил массивов: процедура → `array_rules` → `array_modes`. Путь можно писать без последних `[]`.
- `buckets` — границы бакетов (для `ADJUSTED_VALUE`), одни и те же для обоих срезов. Пример: `pd.value` 0.42 попадает в `(0.3 – 0.6]`.

Ответ: объект конфигурации (`201`).

### 4.3. Получить, изменить, удалить

- `GET /api/configs/{id}` — конфигурация целиком (тело как в 4.2 плюс `id`, `updated_at`).
- `PUT /api/configs/{id}` — то же тело.
- `DELETE /api/configs/{id}` — `204`. Запуски, созданные по ней, остаются.

## 5. Запуски

### 5.1. Запустить прогон

`POST /api/runs`

```json
{ "config_id": "cfg_1" }
```

Ответ (`202`):

```json
{ "id": "r_7f3a", "status": "pending", "config_id": "cfg_1" }
```

Запуск выполняется в фоне. Ручка сразу возвращает `id`, интерфейс не ждёт.

### 5.2. Статус запуска

`GET /api/runs/{id}`

```json
{
  "id": "r_7f3a",
  "status": "running",
  "config_id": "cfg_1",
  "dataset": "RUN-20260827-0001",
  "created_at": "2026-11-06T12:00:00Z",
  "finished_at": null,
  "progress": { "done": 1200, "total": 4004 },
  "current_stage": "normalize",
  "error": null
}
```

- `progress` — количество обработанных файлов из общего числа. В датасете `4004` = 2002 × 2 срезов.
- `current_stage` — `null` у `pending`, `ready` и `error`.
- Фронт опрашивает раз в секунду, пока статус `pending` или `running`.
- При `error` в поле `error` лежит объект ошибки (см. «Ошибки»).

### 5.3. Список запусков пользователя

`GET /api/runs`

```json
{
  "runs": [
    { "id": "r_7f3a", "status": "ready", "config_id": "cfg_1", "name": "Прогон на 06.11", "dataset": "RUN-20260827-0001", "created_at": "2026-11-06T12:00:00Z" }
  ]
}
```

`name` — имя конфигурации на момент запуска.

### 5.4. Остановить запуск

`POST /api/runs/{id}/cancel` → `{ "id": "r_7f3a", "status": "error", "error": { "code": "cancelled", "message": "Остановлено пользователем" } }`. Если запуск уже завершён (`ready` или `error`) — `409 conflict`.

## 6. Журнал этапов

`GET /api/runs/{id}/stages`

```json
{
  "stages": [
    {
      "name": "normalize",
      "title": "Приведение ответов",
      "status": "ready",
      "started_at": "2026-11-06T12:00:01Z",
      "finished_at": "2026-11-06T12:01:10Z",
      "procedure_id": "builtin_normalize",
      "code_ref": { "procedure_id": "builtin_normalize", "source": "file", "path": "procedures/normalize.py", "line": 1 },
      "log": [ { "at": "2026-11-06T12:00:02Z", "level": "info", "message": "Обработано 500 из 4004" } ]
    },
    { "name": "compare", "title": "Сравнение срезов", "status": "running", "started_at": "2026-11-06T12:01:11Z", "finished_at": null, "procedure_id": null, "code_ref": null, "log": [] },
    { "name": "aggregate", "title": "Факты counts", "status": "pending", "started_at": null, "finished_at": null, "procedure_id": "builtin_aggregate", "code_ref": null, "log": [] },
    { "name": "checks", "title": "Проверки", "status": "pending", "started_at": null, "finished_at": null, "procedure_id": null, "code_ref": null, "log": [] }
  ]
}
```

- Этапы идут в порядке: `normalize`, `compare`, `aggregate`, `checks`.
- `code_ref` — куда перейти по клику: id процедуры, путь (для `file`) или `inline`, и номер строки.
- `log` — последние записи этапа. Полный журнал: `GET /api/runs/{id}/stages/{name}/log?after=<индекс>`.

`level` в журнале — `info`, `warn` или `error`.

Полный журнал этапа: `GET /api/runs/{id}/stages/{name}/log?after=<индекс>` → `{ "entries": [ { "at": "2026-11-06T12:00:02Z", "level": "info", "message": "Обработано 500 из 4004" } ], "next": 1 }` — записи начиная с индекса `after` (по умолчанию 0); `next` — индекс, с которого просить дальше.

## 7. Витрина и факты

### 7.1. Итоги (для счётчиков сверху)

`GET /api/runs/{id}/summary`

```json
{
  "applications": 2002,
  "applications_only_before": 0,
  "applications_only_after": 0,
  "applications_changed": 502,
  "applications_changed_share": 0.251,
  "decision_changed": 385,
  "decision_changes": {
    "same": 1617,
    "approve_to_reject": 273,
    "reject_to_approve": 112,
    "decision_other": 0
  },
  "attributes": { "VALUE_CHANGED": 7567, "ATTRIBUTE_NEW": 4108, "ATTRIBUTE_LOST": 3122 },
  "change_sources": { "logic": 218, "data": 167, "both": 0, "none": 0 },
  "checks_fail": 33
}
```

`change_sources` — откуда взялась смена решения (словарь «Откуда смена»), **только по заявкам, где решение изменилось**: сумма всегда равна `decision_changed`. Все четыре ключа есть всегда.

Все числа примера — реальные, с настоящего датасета, `ignore_paths = ["appData.request_id", "appData.createDateTime"]` и пятью проверками организаторов. Технические поля надо исключать всегда: иначе они различаются у всех 2002 заявок и все 385 смен решения получат `data`.

Из 385 смен решения **167 — из-за входных данных**: у всех внешний источник `score_okb` вернул другое значение (в `ext_data[].body.params.data`, следом в `characteristics.score_okb` и в предикторе модели), скор упал, СПР выбрала порог `MFO_ZAIMER_2026_LOW`/`_MID` вместо `MFO_ZAIMER_2026` — и `APPROVE → REJECT`. Остальные 218 — из-за логики (вход тот же). `ATTRIBUTE_NEW`/`ATTRIBUTE_LOST` объясняются составом атрибутов: у разных веток ответа разный набор полей; дублей ключей нет.

`checks_fail` — число строк проверок с `FAIL` (для карточки «Проверки с FAIL»). Поле появляется после этапа `checks`: пока этап не прошёл, его нет. Если проверок в конфигурации нет — `0`.

`applications_only_before` / `applications_only_after` — заявки, которые есть только в одном срезе (сломанный JSON, нет ответа). В витрину, факты и список заявок они не попадают: по просьбе организаторов анализируем только заявки с парой before/after, остальные видны лишь этими счётчиками. `applications` и все остальные числа — по заявкам с парой. Оба поля есть всегда; у запусков до этой правки — `0`. Заявка, у которой ответ не разобрался **в обоих** срезах, не попадает ни в один счётчик — она видна только предупреждением в журнале этапа `normalize`. `applications` в списке датасетов (п. 2.1) — число файлов среза, а не заявок с парой.

Решения (`decision_changes`) уже совпадают с тем, что видно в данных: `APPROVE → REJECT` 273, `REJECT → APPROVE` 112, остальные 1617 заявок с тем же решением.

### 7.2. Факты для сводной таблицы

`GET /api/runs/{id}/facts?dims=CHANGE_TYPE&filter=DIFF_FLAG:1`

Факты — это агрегат «заявки по измерениям». Пользователь сам выбирает измерения.

Параметры:
- `dims` — от одного до трёх разных полей витрины или разреза через запятую. `ARRAY_KEY_1` — первый ключ массива из `ARRAY_KEY`.
- `filter` — строгое равенство `поле:значение`. Условия через `;` объединяются по И, значения одного условия через запятую — по ИЛИ. Пустой `filter` отключает фильтрацию, пустое значение после двоеточия выбирает пустые ячейки. Пустое условие, например завершающая `;`, даёт `400 bad_file`. Для `DIFF_FLAG` допустимы только `0` и `1`.
- Если значение содержит запятую или точку с запятой, передайте в `filter` JSON-объект с непустым массивом строк на поле, например `{"PATH":["appData.key,with;separator"],"DIFF_FLAG":["1"]}`. Поля объединяются по И, элементы массива — по ИЛИ.
- `measure` — `counts` (число строк, по умолчанию) или `counts_distinct_apps` (число уникальных заявок). В обоих случаях показатель возвращается в поле `counts`.
- `limit` — число групп в ответе, от 1 до 5000 (по умолчанию 1000). Группы отсортированы по убыванию показателя. `total_groups` — количество групп после фильтрации до применения `limit`.
- Пустые значения измерений возвращаются как `null`. Неизвестное поле, неверное измерение, показатель или фильтр дают `400 bad_file`. Параметры запроса вне допустимого диапазона или не того типа (`limit` не от 1 до 5000 и т. п.) дают `400 bad_request`: так же везде, где есть `page`, `size` и `limit`.

Пример формы ответа на мини-данных: число строк с различиями по типам.

```json
{
  "dims": ["CHANGE_TYPE"],
  "total_groups": 3,
  "rows": [
    { "CHANGE_TYPE": "VALUE_CHANGED", "counts": 13, "app_ids_ref": "f_000000000001" },
    { "CHANGE_TYPE": "ATTRIBUTE_LOST", "counts": 2, "app_ids_ref": "f_000000000002" },
    { "CHANGE_TYPE": "ATTRIBUTE_NEW", "counts": 1, "app_ids_ref": "f_000000000003" }
  ]
}
```

`app_ids_ref` — ключ для списка заявок (ручка 7.3). Список заявок загружается отдельным запросом. Для новых запросов сохраняются последние 20 000 ссылок сводной на запуск. Ранее сохранённые ссылки из JSON остаются доступны. Если ссылка устарела, повторите запрос фактов.

### 7.3. Заявки по группе фактов

`GET /api/runs/{id}/facts/{app_ids_ref}/apps?page=1&size=50`

```json
{ "page": 1, "size": 50, "total": 2, "apps": [ "MINI-001", "MINI-002" ] }
```

Заявки уникальны и отсортированы по возрастанию id. По умолчанию `page=1` и `size=50`, максимальный `size=500`. `page` или `size` вне диапазона — `400 bad_request`. Для неизвестной ссылки возвращается `404 not_found`.

Пример для группы `ATTRIBUTE_LOST` из ответа выше.

### 7.4. Список заявок с различиями

Параметры:

## 8. Одна заявка подробно

### 8.1. Сравнение атрибутов заявки

`GET /api/runs/{id}/apps/{app_id}/attributes?page=1&size=100`

Параметры:
- `only_diff=1` — только строки с `diff_flag=1`. Без параметра возвращаются все атрибуты.
- `search` — подстрока в `path`, без учёта регистра.
- `page` с 1 (по умолчанию 1), `size` от 1 до 500 (по умолчанию 100). `total` учитывает фильтры и не зависит от страницы. Значения вне диапазона — `400 bad_request`.

Сначала идут строки с `diff_flag=1`, внутри каждой группы — по `path`. Пустые `array_key`, `value_*` и `adjusted_*` возвращаются как `null`. Если заявки нет в запуске, ответ — `404 not_found`.

Это строки витрины одной заявки. Пример — `I32554362`, продукт `751`:

```json
  "size": 100,
  "total": 30,
  "attributes": [
    {
      "path": "decisionResult.product_trials[].scoring.pd.value",
      "array_key": "751",
      "key": "value",
      "value_before": "0.694",
      "value_after": "0.494",
      "adjusted_before": "(0.6 – 1]",
      "adjusted_after": "(0.4 – 0.6]",
      "diff_flag": 1,
      "change_type": "VALUE_CHANGED"
    },
    {
      "path": "decisionResult.product_trials[].cutOff.value",
      "array_key": "751",
      "key": "value",
      "value_before": "0.55",
      "value_after": "0.62",
      "adjusted_before": "(0.3 – 0.6]",
      "adjusted_after": "(0.6 – 1]",
      "diff_flag": 1,
      "change_type": "VALUE_CHANGED"
    }

```

Бакеты в примере подобраны для наглядности, в конфигурации границы задаёт пользователь. `ADJUSTED_VALUE` в этом примере показан по схеме ТЗ, значения не сверены с эталоном.

Атрибут с `ATTRIBUTE_NEW` или `ATTRIBUTE_LOST` имеет пустое значение с той стороны, где его нет: `value_before` или `value_after` равно `null`.

### 8.2. Карточка заявки (до и после)

`GET /api/runs/{id}/apps/{app_id}`

Для окна «почему»: решение, офферы, стоп-факторы, модели и пороги в каждом срезе. Сокращённый пример для `I32554354` (reject → approve):

```json
{
  "app_id": "I32554354",
  "decision_change": "reject_to_approve",
  "before": {
    "decision": "reject",
    "offers": [],
    "products": [
      { "product_id": 15210, "decision": "reject", "reject_reason": "HARDCHECK", "reject_reason_code": "AGELOW@21", "pd_model": "ML_MICRO_LOAN_V1", "pd": 0.637, "cutoff": { "name": "MFO_ZAIMER_2026", "value": 0.55 }, "rules": [ { "name": "AGELOW@21", "hit": true } ] },
      { "product_id": 5123, "decision": "reject", "reject_reason": "HARDCHECK", "reject_reason_code": "AGELOW@21", "pd_model": "ML_MICRO_LOAN_V1", "pd": 0.637, "cutoff": { "name": "MFO_ZAIMER_2026", "value": 0.55 }, "rules": [ { "name": "AGELOW@21", "hit": true } ] }
    ]
  },
  "after": {
    "decision": "approve",
    "offers": [ { "product_id": 15210, "type": "standard" }, { "product_id": 5123, "type": "standard" }, { "product_id": 15210, "type": "manual" } ],
    "products": [
      { "product_id": 15210, "decision": "approve", "reject_reason": null, "reject_reason_code": null, "pd_model": "ML_MICRO_LOAN_V1", "pd": 0.637, "cutoff": { "name": "MFO_ZAIMER_2026", "value": 0.55 }, "rules": [] },
      { "product_id": 5123, "decision": "approve", "reject_reason": null, "reject_reason_code": null, "pd_model": "ML_MICRO_LOAN_V1", "pd": 0.637, "cutoff": { "name": "MFO_ZAIMER_2026", "value": 0.55 }, "rules": [] }
    ]
  },
  "reasons": [ { "text": "Стоп-фактор AGELOW@21 сработал в BEFORE, в AFTER правило отсутствует", "source": "rule", "confidence": "high" } ]
}
```

- В `after.offers` у продукта `15210` два оффера: `standard` и `manual`. Ключ оффера — пара `product_id` + `type`, по одному `product_id` они склеятся. Идентификатор продукта сохраняет исходное представление, число или строку.
- `reasons[].source`: `rule` (стоп-фактор), `score` (смена модели или пересечение порога), `cutoff` (сдвиг порога), `product` (сменился продукт), `data` (возможное влияние входных данных), `unknown`.
- `confidence`: `high` — причина видна в данных, `low` — наша догадка.
- Пустое решение приводится к `other`. Отсутствующие `reject_reason`, `reject_reason_code`, `pd_model`, `pd` и отдельные поля `cutoff` возвращаются как `null`. `rules[].hit = null` означает, что правило не вычислялось. Если заявки нет в запуске или отсутствует её файл в одном из доступных срезов, ответ — `404 not_found`. Отсутствующий манифест или каталог среза даёт `400 bad_file`.
- Новые прогоны сохраняют карту полей в `card_fields.json` на этапе агрегирования. Карточка и причины используют этот снимок. В старых прогонах без снимка детали продуктов читаются по доступной карте, а решения и их переход берутся из сохранённого `apps.csv`.

```json
{
```

## 10. Проверки и отчёт проверок

### 10.1. Результат проверок одной таблицей

`GET /api/runs/{id}/checks?result=FAIL&page=1&size=50`

Строки всех проверок, сколько бы их ни было и кто бы их ни написал. Ниже — **форма**, значения не считались: проверки из `checks/` мы ещё не запускали.

```json
{
  "page": 1,
  "size": 50,
  "total": 11,
  "rows": [
    {
      "check_id": "builtin_attribute_new_loss",
      "check_name": "Изменился состав атрибутов",
      "source": "AFTER",
      "argument": null,
      "numbers": "0 / 500",
      "metric": null,
      "result": "PASS",
      "apps_ref": null,
      "faint": false
    }
  ]
}
```

- `result` — `PASS` или `FAIL`.
- `apps_ref` — список заявок (ручка 7.3). `null`, если заявок нет.
- `check_id` — id процедуры (`builtin_…` или `p_…`), `check_name` — название проверки.
- `numbers` — `"CNT / TOTAL"`; `metric` — число или `null`.
- Проверка, которая упала с ошибкой или не уложилась в таймаут, **не валит запуск**: в таблице она строкой `FAIL` с текстом ошибки в `argument`, `faint: true`; подробности — в журнале этапа `checks` (`level: "error"`).
- `faint` — `true`, если срабатываний мало и уверенности нет. Фронт показывает такую строку бледной, как в ТЗ.

## 12. Мнение ИИ

`GET /api/runs/{id}/ai-review`

Отвечает только при `ready` запуска (иначе `409 not_ready`). Облачная Gemma (Ollama Cloud) даёт короткое второе мнение: что выглядит подозрительно и на что смотреть аналитику. Это не замена проверкам.

**Что уходит модели — только агрегаты**: счётчики из `summary` (п. 7.1), топ-5 причин из п. 9 (`text`, `source`, `affected`, `share`), проверки с `FAIL` (до 10: название, `numbers`, `metric`, `faint`) и число `PASS`, топ-10 самых изменившихся атрибутов (путь и число заявок). Заявки, их id и значения атрибутов **не отправляются**.

Мнение считается в фоне сразу после `ready` и сохраняется. Повторные запросы не обращаются к модели.

Готово:

```json
{
  "status": "ready",
  "text": "Итог: решение изменилось у 385 заявок: 273 стали отказом, 112 — одобрением...\nЧто выглядит подозрительно:\n- ...\nНа что посмотреть:\n- ...",
  "generated_at": "2026-11-07T12:05:00Z",
  "model": "gemma4:31b",
  "inputs": ["summary", "reasons", "checks", "top_changed_attributes"]
}
```

Считается — `{ "status": "pending" }`: фронт показывает «Считаем…» и опрашивает ручку раз в несколько секунд.

Модель недоступна (нет ключа, таймаут, лимит, ошибка сервиса) — `{ "status": "error", "error": { "code": "unavailable", "message": "…" } }`. Фронт показывает `message`, отчёт остаётся доступен. Повторный запрос через минуту пробует снова.

`text` — обычный текст с переносами строк, не HTML и не Markdown; фронт выводит его как текст. `inputs` — что показали модели. В HTML-отчёте (п. 11) то же мнение лежит отдельным блоком «Мнение ИИ».

## Ошибки

Любая ошибка — в одном виде:

```json
{ "error": { "code": "bad_file", "message": "Не получилось прочитать процедуру: нет функции run" } }
```

| `code` | HTTP | Когда |
|---|---|---|
| `bad_file` | 400 | файл или датасет не читается или не того формата |
| `bad_request` | 400 | неверный запрос: нет обязательного поля или оно не того типа (в `message` — поле и причина) |
| `bad_code` | 400 | код процедуры не проходит проверку контракта, в `message` — строка и причина |
| `no_id_column` | 400 | не нашли, по какому полю склеивать заявки |
| `not_found` | 404 | нет такого датасета, конфигурации, запуска, процедуры или заявки |
| `not_ready` | 409 | запрос к отчёту или фактам, а запуск ещё не `ready` |
| `conflict` | 409 | нельзя изменить или удалить встроенную процедуру; нельзя остановить уже завершённый запуск |
| `cancelled` | — | запуск остановлен пользователем (в поле `error` статуса запуска) |
| `interrupted` | — | запуск прерван перезапуском сервера (в поле `error` статуса запуска и этапа); запустите прогон заново |
| `internal` | 500 | всё остальное |

Фронт показывает `message` пользователю как есть.
Ошибка этапа записывается в его журнал и в `error` запуска. У запуска `status` становится `error`, а у этапа — тоже.

## Порядок работы на хакатоне

1. **Сейчас:** бэк делает ручки с **выдуманными** ответами ровно как тут: датасеты, конфигурации, запуск, статус, этапы, итоги, заявки, атрибуты, отчёт. Фронт работает с ними.
2. **Дальше:** бэк заменяет выдумку на настоящий расчёт. Фронт ничего не замечает.
3. **Минимум для показа:** запуск и статус (5.1–5.2), этапы (6), итоги (7.1), список заявок (7.4), атрибуты заявки (8.1), отчёт (11). Остальное — по мере сил.
