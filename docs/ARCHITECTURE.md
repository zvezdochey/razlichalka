# Архитектура и выбор стека

Одна страница — ответ на шаг 9 демо: почему так, какие были альтернативы, что замеряли, чем платим.

## 1. Стек

- **FastAPI + pandas** (бэк). Данные табличные — 291 тыс. строк витрины, сравнение, группировки; pandas делает это
  в пару строк. FastAPI даёт валидацию и Swagger (`/docs`) бесплатно, а фронт и бэк договариваются по `docs/api.md`.
- **React + Vite + TypeScript** (фронт). Типы совпадают с договором API, Vite собирает быстро.
- **Docker Compose**: `docker compose up --build` — и бэк, и фронт (nginx проксирует `/api` на бэк). По README
  поднимается на чистой машине.

Альтернативы: Node-бэк (хуже с таблицами), Django (тяжелее для набора ручек, которым нужен только JSON).

## 2. Хранение

Результат запуска — файлы в томе `razlichalka_var`: `comparison.csv`, `segments.csv`, `apps.csv`, `checks.csv`,
`summary.json`. Разделитель `;` — как в выданном примере витрины организаторов, так их проверки читают наш файл
без переделок. Конфигурации и список запусков — JSON-файлы, запись атомарная (временный файл + замена). Сверху —
кэш в памяти (`lru_cache`) на запуск.

**Почему не БД:** запуск пишется один раз и дальше только читается целиком; формат совпадает с форматом
организаторов; ничего не надо поднимать и мигрировать. **Чем платим:** нет индексов и запросов «из коробки» —
фильтры и группировки делаем в pandas по загруженной таблице; кэш занимает память (~41 МБ на запуск); данные
нескольких запусков одновременно в памяти не помещаются бесконечно (кэш ограничен 4 и 16 запусками).

## 3. Где параллелится

Честно: **конвейер идёт последовательно** — весь прогон занимает ~10 с (по замерам, ниже), это в ~3 раза быстрее
планки ТЗ «отлично» (≤ 30 с), и усложнять его не стали. Параллельность есть в двух местах:
- запуски идут в фоне в пуле из 2 потоков (`ThreadPoolExecutor`), интерфейс не блокируется, запуск можно
  остановить;
- проверки исполняются в отдельном процессе (см. п. 4).

Если понадобится ускорять: самый долгий шаг — `compare` (4,5 с), следом два `normalize` по 2,4 с — их можно
пустить параллельно по процессам.

## 4. Как исполняем чужой код

Проверки (`check_*.py` организаторов и написанные в приложении) исполняются в **отдельном процессе**
(`multiprocessing`, режим `spawn`) с таймаутом: 60 с на проверку, 15 с на загрузку кода. Витрина доступна через
`MartAPI` — тот же интерфейс, что в `ПАКЕТ/ЗАДАНИЕ/checks`. Исключение или таймаут одной проверки не роняют
прогон: вместо её строк в отчёте появляется служебная строка с текстом ошибки. **Ошибка проверки ≠ FAIL**:
FAIL — это вывод проверки о данных, а ошибка — что проверка не отработала.

Встроенные процедуры (правила разбора массивов, карта полей, пути для разрезов) — обычные `.py` в
`backend/procedures/`; это данные (словари), их можно открыть из журнала как «код этапа».
Пока что их грузим в процессе приложения — это наши файлы из репозитория; пользовательские процедуры,
написанные в приложении, надо исполнять так же изолированно, как проверки (в плане — E13).

## 5. Сводная таблица

Агрегат считает **сервер** (`/facts`), фронт только рисует: в браузер не уходит 291 тыс. строк, а раскладка
по любым двум измерениям (путь атрибута, тип изменения, ключ массива…) — это группировка в pandas. Готовую
pivot-библиотеку не брали: она ждёт сырые строки на клиенте, а нам нужны проваливание до заявки и атрибута и
серверные фильтры; цена — собственный небольшой компонент, меньше возможностей «из коробки».

## 6. «Логика или данные»

Для каждой смены решения смотрим, **изменился ли вход**: если у заявки различаются входные данные (после
исключения технических полей `request_id` и `createDateTime`) — источник `data`, если вход тот же — `logic`.
На настоящем датасете из 385 смен решения **167 — из-за входных данных** (внешний источник `score_okb` вернул другой
скор, СПР выбрала другой порог), **218 — из-за логики**. Технические поля исключаем всегда, иначе они различаются
у всех 2002 заявок и все смены ушли бы в `data`.

## 7. Узкое место

Что замеряли: этапы конвейера и первый вызов каждой ручки отчёта (`pipeline/tools/bench.py`, подробно —
[docs/perf.md](perf.md)). Машина: ноутбук, 12 логических ядер, 15,8 ГБ, Python 3.12, pandas 3.1, без Docker.
Датасет: 2002 заявки × 2 среза, 291 151 строка витрины.

| Шаг конвейера | с |
|---|---:|
| normalize (два среза) | 4,8 |
| compare | 4,5 |
| segments + summary | 1,1 |
| **всего** | **10,4** |

Узким местом оказался не конвейер, а **первое открытие отчёта**: сводная заново читала с диска 45 МБ витрины и
приводила колонки к типам. Ускорение — **прогрев кэшей** в конце запуска (0,7 с, до статуса `ready`):

| Ручка | до, мс | после, мс |
|---|---:|---:|
| сводная `/facts` | 512 | 29 |
| смена раскладки | 486 | 17 |
| переход к заявке `/apps/{id}/attributes` | 197 | 15 |

Цена: +0,7 с к запуску и ~41 МБ памяти на запуск. Альтернатива — хранить витрину в parquet; не стали из-за новой
зависимости, а прогрев уже убрал задержку с пути пользователя.

## 8. Что не успели

- Пользовательские процедуры (рабочая область) в изолированном процессе — сейчас так изолированы только проверки.
- Обработка порциями по мере поступления ответов вместо «сначала всё, потом сравнение».
- Параллельный `normalize` двух срезов по процессам; parquet вместо CSV.
- Мнение ИИ о результате (резерв).
